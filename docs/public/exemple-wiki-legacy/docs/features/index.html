Vue d'ensemble ​

Objectif ​

Site web de petites annonces (v1.0.2, GPL v3) permettant à des particuliers de publier, rechercher et gérer des annonces classées par catégorie et par région, avec un back-office d'administration pour modérer le contenu et paramétrer les référentiels.

Problématique ​

L'application fournit une place de marché de petites annonces : un visiteur peut déposer une annonce sans compte (un compte est alors créé automatiquement), la faire valider par email, puis la modifier, la prolonger ou la supprimer via des liens à jeton. Les utilisateurs inscrits peuvent répondre aux annonces, les signaler, les noter, les mettre en favoris et évaluer les autres utilisateurs. L'administrateur modère (suppression, sponsorisation, bannissement).

Domaine métier ​

Petites annonces en ligne (classifieds), mise en relation entre particuliers, modération communautaire.

Hypothèses ​

  • Basé sur admin/*.php, le rôle administrateur est l'utilisateur id = 1 (aucun modèle de rôles).
  • La colonne sponsored suggère une mise en avant payante ou éditoriale ; aucun paiement n'est implémenté.
  • Les colonnes expirednotice et sponsoredon ne sont pas exploitées ; l'expiration n'est pas appliquée automatiquement (aucune tâche planifiée) : une annonce expirée reste visible.
  • La recherche par prix (colonne ar) référence une colonne inexistante : fonctionnalité intentionnelle mais cassée.
  • La connexion par email, annoncée dans le formulaire, n'est pas implémentée.
  • Les *-create de l'admin pour user_ban, response, report, ad_review, user_review sont informatifs (aucun formulaire) : ces entités ne sont créées que côté front.
  • Le « faux succès » pour un utilisateur banni ($last = 666666) est un comportement métier voulu (shadow ban).
  • Les six templates d'email sont stockés dans static-content (ids 1 à 6) ; les ids > 6 sont des pages éditoriales.

Rôles utilisateurs ​

Rôle 1 : Visiteur anonyme ​

  • Description : Internaute non connecté.
  • Niveau d'Accès : Lecture publique ; actions sur annonce via liens à jeton (id + code).
  • Fonctions Principales :
    • Parcourir, rechercher, consulter et imprimer les annonces
    • Consulter catégories, régions, pages statiques, profils publics
    • Déposer une annonce (création automatique d'un compte)
    • Activer, modifier, prolonger ou supprimer une annonce via lien reçu par email
    • Envoyer une annonce à un ami
    • S'inscrire, se connecter, demander un mot de passe perdu

Rôle 2 : Utilisateur connecté ​

  • Description : Détenteur d'un compte (session PHP).
  • Niveau d'Accès : Visiteur + actions d'interaction nécessitant une session.
  • Fonctions Principales :
    • Répondre à une annonce, signaler un abus
    • Noter une annonce, noter un utilisateur
    • Gérer ses favoris
    • Modifier son profil et son mot de passe
    • Déposer une annonce activée immédiatement

Rôle 3 : Administrateur ​

  • Description : Utilisateur id = 1.
  • Niveau d'Accès : Accès total au back-office /admin et au bannissement front (user-ban.php).
  • Fonctions Principales :
    • CRUD sur annonces, utilisateurs, catégories, régions, durées, contenus statiques
    • Sponsoriser / dé-sponsoriser une annonce
    • Consulter et supprimer réponses, signalements, avis, bannis
    • Bannir un utilisateur (suppression de ses annonces)
    • Gérer son profil et son mot de passe d'administration

Flux utilisateurs principaux ​

Flow 1 : Dépôt d'annonce par un visiteur ​

Acteurs : Visiteur anonyme Étapes :

  1. Remplir le formulaire de dépôt (coordonnées, titre, description, catégorie, région, durée, image, conditions)
  2. Validation ; contrôle de bannissement (email / IP)
  3. Création de l'annonce inactive avec jeton ; création d'un compte si l'email est inconnu
  4. Envoi des emails d'activation (et d'inscription)
  5. Clic sur le lien d'activation Résultat : Annonce active et visible dans les listes.

Flow 2 : Dépôt par un utilisateur connecté ​

Acteurs : Utilisateur connecté Étapes :

  1. Remplir le formulaire de dépôt
  2. Activation immédiate Résultat : Annonce publiée sans validation par email.

Flow 3 : Recherche et consultation ​

Acteurs : Visiteur, Utilisateur Étapes :

  1. Accueil (redirection vers la liste complète)
  2. Filtrer par catégorie, région, mots-clés, prix
  3. Ouvrir le détail, imprimer ou envoyer à un ami
  4. (Connecté) répondre, signaler, noter, ajouter aux favoris Résultat : Contact avec le déposant ou conservation de l'annonce.

Flow 4 : Gestion de l'annonce par jeton ​

Acteurs : Déposant (anonyme ou connecté) Étapes :

  1. Ouvrir le lien reçu par email
  2. Choisir modification, prolongation ou suppression Résultat : Annonce mise à jour, prolongée de N jours ou supprimée.

Flow 5 : Compte utilisateur ​

Acteurs : Visiteur, Utilisateur Étapes :

  1. Inscription (+ activation par email) ou création automatique via dépôt
  2. Connexion (décision : identifiants valides ou message d'erreur)
  3. Édition du profil / changement de mot de passe ; mot de passe perdu par email Résultat : Compte opérationnel.

Flow 6 : Modération ​

Acteurs : Utilisateur, Administrateur Étapes :

  1. Un utilisateur signale une annonce (email à l'administrateur)
  2. L'administrateur consulte les signalements dans le back-office
  3. Suppression de l'annonce, sponsorisation ou bannissement de l'utilisateur Résultat : Contenu retiré et utilisateur bloqué par email/IP.

Flow 7 : Administration des référentiels ​

Acteurs : Administrateur Étapes :

  1. Connexion à /admin
  2. Création / édition / réordonnancement des catégories, régions, durées, contenus statiques Résultat : Référentiels et emails mis à jour pour le front.

Préoccupations transversales ​

Authentification & Autorisation ​

Session PHP native ; mots de passe en clair ; administrateur codé en dur (id = 1) ; actions sur annonces autorisées par jeton id + code indépendant de la session ; aucune protection CSRF ; actions destructrices en GET.

Gestion des Erreurs ​

Messages d'erreur accumulés dans $errors / $_SESSION[login_error] et affichés dans les templates ; faux succès silencieux pour les bannis.

Logging & Monitoring ​

Aucun logging structuré ; debug() affiche des messages dans la page.

Validation des Données ​

Casts (int), strip_tags, regex dans les contrôleurs ; aucun échappement HTML en sortie ; validation mélangée à la logique de page.

Pagination ​

Librairie PEAR Pager (15 par page) pour listes publiques et admin.

Gestion des Fichiers ​

Images dans upload/AAAA/MM/JJ/{picture,thumb} via GD.

Layout et Navigation ​

Bootstrap commun (common.php) : arbres catégories/régions, compteurs, menu admin dynamique, fil d'Ariane.

Historique d'audit de l'inventaire ​

Audit du 2026-10-07 ​

Auditeur : Business Analyst Senior (CLI Claude)

Objectif : Auditer l'inventaire fonctionnel initial contre la codebase réelle pour identifier les features, rôles ou flux manqués.

Résultats :

  1. Couverture des Scripts PHP : Tous les 62 scripts PHP identifiés (25 publics + 37 admin) sont correctement mappés aux 15 features de l'inventaire. Aucune feature manquante identifiée.

  2. Couverture des Rôles : Les 3 rôles documentés (Visiteur anonyme, Utilisateur connecté, Administrateur) couvrent complètement les cas d'usage. Aucun rôle supplémentaire requis.

  3. Couverture des Flux : Les 7 flux utilisateurs documentés (Dépôt, Recherche, Gestion par jeton, Compte, Modération, Administration) couvrent tous les parcours utilisateur identifiés dans la codebase.

  4. Correction de Dépendance Identifiée : La Feature 5 (Authentification) déclare une dépendance sur Notifications Email, mais était classée avant elle. Correction appliquée : Notifications Email (anciennement Feature 10) a été réordonnée en Feature 5 ; Authentification déplacée à Feature 6. Les numéros des features suivantes ont été ajustés en conséquence (Recherche=7, Gestion Compte=8, Favoris=9, Avis=10, Interactions=11, Dépôt=12, Cycle de Vie=13, Modération=14, Administration=15).

  5. Aucune Feature Technique Manquante : Les préoccupations transversales (Pagination, Gestion des Fichiers, Layout, Validation, etc.) sont correctement documentées comme Cross-Cutting Concerns et ne nécessitent pas de features distinctes.

Conclusion : L'inventaire est complet et cohérent. La réorganisation des features a corrigé l'inconsistance de dépendance détectée. Prêt pour les étapes suivantes de migration (spécification détaillée des features, planification backend/frontend).
